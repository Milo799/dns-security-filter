# Windows DNS 安全过滤中间件 · AI 能力规划方案

**版本**：V1.0
**日期**：2026-10-13
**状态**：待评审

---

## 1. 概述

### 1.1 现状

平台以"规则 + 名单"为核心的五层检测链已稳定运行 40 余天（零重启、零 ERROR），日均 460 万查询、拦截率约 8%，在库威胁情报 600 万条。检测能力成熟可靠。

### 1.2 能力缺口

检测链全部是**确定性规则**（名单匹配 / 注册年龄阈值 / 情报投票），而 460 万条/日的查询数据目前仅用于统计展示（COUNT / GROUP BY），**数据价值利用不足 5%**。具体表现为四个空白：

| 空白 | 现状 | 后果 |
|---|---|---|
| 未知威胁自主发现 | 100% 依赖外部情报源 | 源未收录的新威胁无法发现 |
| 内网失陷主机发现 | 完全空白（只按域名判，不看谁在查） | 中毒主机无法定位 |
| 误报治理 | 纯人工研判 + 手工加白 | 每次误伤都消耗人工 |
| 海量拦截数据的价值 | 仅列表展示 | 无法归纳出威胁趋势 |

### 1.3 方案定位

**AI 不改变现有检测链，而是新增"旁路 AI 分析层"**：

- **只读旁路**：AI 全部做离线批处理，只读数据库，绝不进入 `process_query` 热路径——主链路零风险；
- **建议而非判定**：AI 产出"建议 + 证据"，是否生效由人工确认——安全判定可解释、可审计；
- **闭环回灌**：人工确认的结果回灌名单/配置，系统能力随时间自主增强。

## 2. AI 能力全景（六大方向）

| # | 方向 | 解决的空白 | 一句话定位 |
|---|---|---|---|
| A | 域名智能识别 | 未知威胁发现 | 识别 DGA 恶意域 + DNS 隧道外泄 |
| B | 威胁情报增强 | 情报质量治理 | 智能融合加权 + 源质量评分 |
| C | 误报治理 | 误报治理自动化 | 误伤评分 + 一键加白推荐 |
| D | 告警降噪归纳 | 海量数据价值 | 数万拦截聚成"今日 N 个威胁族群" |
| E | 客户端行为建模 | 失陷主机发现 | 每台主机行为基线 + 异常偏离识别 |
| F | LLM 智能中枢 | 人机交互升级 | 研判报告生成 + 自然语言运维 |

其中 A、C、D、E 是**算法/统计层**（纯 Python，生产侧稳定可靠），B 是**情报治理层**，F 是**LLM 层**（灵活、可换模型、部署在分析侧）。

## 3. 各方向详细设计

### 3.1 A · 域名智能识别（DGA + 隧道）

**目标**：发现不在任何名单里的新型恶意域名与隐蔽信道。

| 项 | 内容 |
|---|---|
| 输入 | 域名首现记录（新增）、查询类型、子域结构、客户端 IP |
| 技术 | **DGA**：字符 n-gram 语言模型（用已知正常域名做白样本、已知 DGA 家族做黑样本）+ 统计特征（长度 / 数字比 / 信息熵 / 辅音连缀）；**隧道**：子域长度与熵分布 + TXT/NULL/MX 异常类型占比 + 单客户端对单一父域的高频查询 |
| 输出 | 每日"疑似 DGA 域名清单"（含评分与证据）、疑似隧道会话告警 |
| 接口 | 新增 `GET /api/ai/dga-suspects`、`GET /api/ai/tunnel-suspects` |
| 工作量 | 3~5 天（纯算法，无需训练基础设施） |
| 风险 | 低——只读分析，误报仅进报告不拦截 |

**关键技术决策**：DGA 检测用**轻量统计模型**而非深度学习——可解释（能说明"为什么像 DGA"）、无需 GPU、冷启动即可用。

### 3.2 B · 威胁情报增强

**目标**：把情报从"简单投票"升级为"带置信度的智能融合"，并治理源质量。

| 项 | 内容 |
|---|---|
| 输入 | 各情报源命中记录、历史误伤率、更新频率、覆盖率 |
| 技术 | 源质量动态评分（历史准确率 × 更新及时性 × 覆盖度）；多源加权融合替代简单投票；失效 IOC 自动识别（长期无命中 + 域名已下线） |
| 输出 | 源质量看板、失效条目清理建议、加权拦截置信度 |
| 接口 | `GET /api/ai/intel-quality` |
| 工作量 | 1 周 |
| 风险 | 低 |

### 3.3 C · 误报治理（高价值，直接替代人工）

**目标**：github.com / ip.sb 这类误伤由系统自动识别并推荐加白，不再每次人工查。

| 项 | 内容 |
|---|---|
| 输入 | 拦截记录、人工加白历史（学习"什么是误伤"）、域名业务特征 |
| 技术 | 误伤评分模型：多客户端共访（业务常用性）、访问时段规律性（工作时间=业务）、域名年龄与 whois 备案、被拦后客户端持续重试（用户依赖）、TLD 业务属性 |
| 输出 | 每日"疑似误伤 TOP N"，附证据链，支持一键加白 |
| 接口 | `GET /api/ai/false-positive`，`POST /api/ai/false-positive/{domain}/whitelist` |
| 工作量 | 1 周 |
| 风险 | 中——加白建议仍需人工确认（红线） |

### 3.4 D · 告警降噪归纳

**目标**：把"每天 20 万条拦截记录"压缩成"今日 12 个威胁族群"，让大屏从"看数字"变"看故事"。

| 项 | 内容 |
|---|---|
| 输入 | filter_log 拦截记录（域名、客户端、时间、命中源） |
| 技术 | 按（父域族 / 客户端 / 时间窗 / 命中源）多维聚类 + 威胁族群画像（规模、活跃度、类型分布） |
| 输出 | 威胁族群榜单 + 族群详情页 |
| 接口 | `GET /api/ai/threat-clusters` |
| 工作量 | 3~5 天 |
| 风险 | 低 |

### 3.5 E · 客户端行为建模（补最大安全空白）

**目标**：发现内网失陷主机——当前平台只看"查了坏域名"，不看"哪台机器行为异常"。

| 项 | 内容 |
|---|---|
| 输入 | 客户端 IP × 域名 × 时间的查询序列 |
| 技术 | 每台主机建立查询基线（域名类别分布、QPS、活跃时段、新域名尝试率）；偏离度评分（当前行为 vs 历史基线）；失陷特征（突发大量新域名、周期性信标回连、DGA 域聚集） |
| 输出 | 异常客户端榜单（疑似失陷主机）+ 异常原因 |
| 接口 | `GET /api/ai/client-anomalies` |
| 工作量 | 2 周（含基线冷启动期 7~14 天） |
| 风险 | 中——基线期需要积累数据 |

### 3.6 F · LLM 智能中枢

**目标**：把结构化结论翻译成自然语言，提供对话式运维能力。

用户已明确：DNS 解析信息无需考虑敏感性，可用外部 LLM。

| 项 | 内容 |
|---|---|
| 输入 | A~E 各模块产出的结构化结果 + 域名情报上下文 |
| 能力 | ① 每日威胁研判报告（自然语言）；② 大屏自然语言问答（"昨天为什么拦了 xx"）；③ 域名研判摘要（命中源 + whois + 行为 → 一段话结论）；④ 自然语言查询（"给我看今天的隧道告警"） |
| 部署 | **LLM 研判放在分析侧，不跑在生产**（见 §5 架构）——生产零风险、模型可自由切换 |
| 工作量 | 离线研判 1 周；在线问答 2 周 |
| 风险 | 低（仅文本生成，不参与判定） |

## 4. 数据基础与缺口补齐（必须先做）

**当前缺口**：`filter_log` 只记录拦截 / 白名单放行 / 观察三类事件，**普通放行域名只计数不记明细**（detectors.py 性能优化）。而 A/D/E 三个方向都需要"常态查询"数据。

### 4.1 补齐方案：域名首现表（推荐）

新增轻量表 `domain_first_seen`，只记**每个域名首次出现**的一行：

```sql
CREATE TABLE domain_first_seen (
    domain       VARCHAR PRIMARY KEY,   -- 小写无尾点
    first_seen   DATETIME NOT NULL,     -- 首次查询时间
    first_client VARCHAR DEFAULT '',    -- 首个查询客户端
    qtype        VARCHAR DEFAULT ''     -- 查询类型
);
```

- **写入逻辑**：进程内 bloom filter 或 LRU 判"是否见过"，首次见则入库（INSERT OR IGNORE，幂等）；
- **开销**：极低——绝大多数域名只写一次，后续命中布隆过滤器零写库；
- **价值**：DGA 检测的"新域名"信号、客户端"新域名尝试率"指标、威胁狩猎的时间起点全部来自这张表；
- **备选**：若担心写入量，可加开关 `ai_first_seen_enabled`（默认开）。

> 该表是 A/D/E 三个方向的共同地基，P0 必须先做。

## 5. 部署架构（关键设计）

**核心原则：生产侧只做"确定性特征提取"，LLM 研判放在分析侧。**

```
┌─────────────────────────────────────────────────────────┐
│ 生产服务器（172.16.0.191）                                │
│                                                          │
│  检测链 L1-L5（不变）                                     │
│       │ 写 filter_log / domain_first_seen                │
│       ▼                                                  │
│  AI 特征提取器（新增，低峰批处理）                          │
│  · DGA 评分 · 隧道特征 · 误报评分 · 聚类 · 行为基线         │
│       │ 产出结构化结论（存 ai_findings 表）                │
│       ▼                                                  │
│  AI 洞察 API（只读）+ 大屏洞察面板                         │
└──────────────────┬──────────────────────────────────────┘
                   │ 结构化特征（非原始日志）
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 分析侧（工作站 / 分析服务）                                │
│                                                          │
│  LLM 研判中枢                                             │
│  · 每日威胁报告 · 域名研判摘要 · 运维问答                   │
│  · 可自由切换模型（DeepSeek / 通义 / Claude / 私有化）      │
└─────────────────────────────────────────────────────────┘
```

**为什么这样拆**：

- 生产服务器出站需走内网代理且 LLM API 域名可能未放行——特征提取是纯计算，不依赖外网，稳定可靠；
- LLM 调用集中在分析侧，模型可自由切换、出问题不影响生产、可复用现有 WorkBuddy 环境；
- 生产与分析侧通过 `ai_findings` 表（结构化结论）解耦。

## 6. 分阶段实施路线

| 阶段 | 周期 | 内容 | 交付物 | 验证标准 |
|---|---|---|---|---|
| **P0 地基** | 第 1 周 | ① 域名首现表 + 采集<br>② DGA 识别原型<br>③ 隧道检测原型 | 每日 DGA/隧道报告 | 对已知 DGA 样本召回 >90%，误报可控 |
| **P1 治理** | 第 2~3 周 | ④ 误报识别 + 一键加白<br>⑤ 告警聚类族群<br>⑥ 大屏 AI 洞察面板 | 误报 TOP N + 族群榜单 | 误报推荐准确率（抽样人工复核） |
| **P2 建模** | 第 4~6 周 | ⑦ 客户端行为基线（冷启动 14 天）<br>⑧ 失陷主机识别<br>⑨ 情报质量评分 | 异常客户端榜单 | 失陷检出（红队验证 / 已知案例回放） |
| **P3 智能中枢** | 第 7~10 周 | ⑩ LLM 离线研判报告<br>⑪ 大屏自然语言问答<br>⑫ 闭环自进化 | 日报 + 问答面板 | 报告可读性、问答准确率 |

**里程碑交付节奏**：每周有可演示成果，每阶段结束评审后再进下一阶段。

### 7.1 新增数据表

| 表 | 用途 | 量级预估 |
|---|---|---|
| `domain_first_seen` | 域名首现（地基） | 数万行/月，长期数十万 |

### 7.2 新增 API（只读为主，加白需确认）

```
GET  /api/ai/dga-suspects        # 疑似 DGA 域名
GET  /api/ai/tunnel-suspects     # 疑似隧道会话
```

## 8. 风险评估与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| AI 误判影响主链路 | —（已规避） | 旁路只读架构，AI 不进 `process_query` |
| 误报加白建议错误 | 中 | 红线：加白必须人工确认；建议附完整证据链 |
| 行为基线误报失陷主机 | 中 | 14 天冷启动 + 仅输出"嫌疑"不自动处置 |
| LLM 研判不准确 | 低 | LLM 只做"翻译/归纳"，结论来自算法层证据 |
| DB 增长（首现表+结论表） | 低 | 首现表幂等去重、结论表设保留期清理 |
| 生产资源占用 | 低 | 批处理放凌晨低峰；平台 16G 内存当前仅用 4G |

## 9. 资源与成本估算

| 资源 | 需求 | 说明 |
|---|---|---|
| 算力 | 现有生产机即可 | 批处理利用低峰空闲资源，16G 内存充足 |
| LLM | 按 token 计费（分析侧） | 每日报告 + 研判，预估月成本 ¥数十~数百级；可选私有化小模型（零 API 成本但需 GPU） |
| 存储 | 新增 < 1G/月 | 首现表 + 结论表，设保留期 |
| 人力 | AI 辅助开发 | 本方案全程 AI 辅助实现 |

**对比参照**：微步 ThreatBook 付费版 ¥468/6个月（60 条/天）只能做"失陷检测富化"；本方案 P0~P2 交付的自主发现 + 误报治理 + 失陷主机识别，能力远超且为自有资产。

## 11. 一句话总结

> **现有系统是"盾"（拦截已知威胁），本方案给它装上"眼"（自主发现未知威胁与失陷主机）和"嘴"（LLM 自然语言运维）——全部旁路、零主链路风险、建议需人工确认，让系统从"被动防御"进化为"自主感知"。**

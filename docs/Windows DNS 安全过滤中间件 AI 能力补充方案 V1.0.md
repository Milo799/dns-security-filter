## 0. 前置红线：名单变更只能由人做（不可协商）

> **白名单/黑名单直接影响业务系统能否被访问——改错就是业务中断。**
>
> 因此本方案中的所有能力都被限定为 **只读分析 + 出建议**：
> - A3（名单质量自省）、A4（白名单通配审计）、A5（影响面预演）**只产出报告**，
>   报告里给出"建议动作 + 影响面 + 证据"，**不执行任何名单变更**；
> - 任何名单改动一律由人在管理端页面完成，或在用户**逐条点名**后由 MCP 代为执行
>   （MCP 默认只读，且写工具需 `confirm=true`）；
> - 系统层面：MCP 服务默认 `DNSF_MCP_ALLOW_WRITE=0`；写操作双重审计留痕。
>
> 这条红线优先于本方案的一切功能设计。

## 1. 判断：AI 能力有四个维度，MCP 只补了其中一维

已有交付（迭代 49 AI 旁路分析 + 迭代 50 MCP）覆盖了前两维，但第三、四维基本空白：

| 维度 | 含义 | 现状 |
|---|---|---|
| **感知**（发现未知） | 从流量里发现规则抓不到的东西 | 部分覆盖：DGA / 隧道 / 族群 / 客户端基线。**但有盲区（见 §2.4）** |
| **决策**（研判与建议） | 把发现变成可判断的结论 | 覆盖：误报评分 / 情报质量 / LLM 中枢。**但精度与自省不足** |
| **行动**（闭环执行） | 让结论真正落地 | ✅ **MCP 已解决**（16 工具，Agent 可操作） |
| **自省**（自身健康与策略质量） | 系统对自己做体检 | ❌ **几乎空白**：名单质量、告警阈值、自身故障自识别都没有 |

一句话：**MCP 解决了「谁在操作」，但「看得更全、判得更准、系统自己会体检」这三件事还没做。**

### 2.2 🔴 关键发现：客户端维度 100% 缺失（P0）——**两层原因，第二层更根本**

#### 第一层：代理二进制是 8 个提交之前的旧产物（已定位到具体版本号）

| 检查 | 结果 |
|---|---|
| `filter_log.client_ip` | **910 万行全部为空串**（全库仅 2 行有值 = 我手工 `dig +subnet` 的测试） |
| `domain_first_seen.first_client` | **36,576 行全部为空串** |
| 平台 ECS 解析 | ✅ **正常**：手工发带 ECS 的查询正确记录 `client_ip=203.0.113.77` |
| **经代理 · 自带 ECS** | ✅ **透传正常**：`dig +subnet=198.51.100.9/32` → 日志记到 `198.51.100.9`（`forward()` 原样转发不改报文） |
| **经代理 · 不带 ECS** | ❌ **不注入**：抓包显示 OPT 记录 **RDLENGTH=0**（有 OPT 但里面没有 ECS option） |
| 生产代理二进制 | ❌ 编译自 **rev `49305c0`（2026-09-01 17:48）**，落后当前源码 **8 个提交**；该版本无 `proxy/ecs.go`、`config.go` 无 `EcsEnabled` |

**根因 = 部署流程与源码脱钩（完整时间线，全部有据可查）**：

| 时间（+0800） | 事件 | 证据 |
|---|---|---|
| 09-02 15:48 | `go build` 编译（当时源码 = `49305c0`，尚无 ECS） | 生产机 `/root/.bash_history`（带 epoch 时间戳） |
| 09-02 15:49 | 产物 `bin/dns-proxy` 落盘 | 文件 mtime |
| **09-03 18:58** | **ECS 功能提交 `63d2577`（Task#158，+360 行）** | git |
| 09-04 08:26 | 源码副本 `git pull` → 更新到 `63d2577`（`ecs.go` 落盘） | 文件 mtime |
| 09-04 08:27 / 08:28 | **又跑了两遍 `install-proxy.sh`——但没有重新编译** | history |
| 09-04 08:28 | `/opt/.../bin/dns-proxy` = 09-02 那份旧产物 | 与 `/app/.../bin/dns-proxy` **md5 完全相同**（`e22102f9…`） |

一句话：`install-proxy.sh` 原先无条件安装 `bin/dns-proxy`（**gitignore 的预编译产物**），拉完代码没重编，就把旧产物又装了一遍。已在脚本里加固为硬校验（见 §8）。

#### 第二层（更根本）：即使修好注入，依然拿不到终端 IP

生产抓包 1000 包的实测：

| 观测 | 结果 |
|---|---|
| 代理入向查询来源 | **1000/1000 全部来自 `172.16.7.1`**；排除它后 30s 窗口内**无任何其他来源** |
| 平台入向来源 | 15/15 来自代理 `172.16.0.192` |
| `172.16.7.1` 身份 | ping / TCP 全端口 / DNS 直查**均无响应**（黑盒，典型安全设备或防火墙 DNS 代理形态，**需网络组确认**） |

即真实拓扑是：**终端 → `172.16.7.1`（唯一上游转发器）→ 代理 → 平台**。代理看到的对端恒为这一个地址，**注入 ECS 只能得到 `172.16.7.1` 一个值**——"多客户端共访"照样算不出来。

**后果（不是理论，是已经发生）**：
- 误报识别最强特征「多客户端共访」（权重 0.32）**算不出来** → 生产 `false_positive` 结论 **0 条**
- 失陷主机识别（`client_anomaly`）**不产出** → MCP 的 `client_anomalies` 与 AI 大屏对应面板都是空的
- 任何"按客户端"的研判（谁在被攻击、哪台机器可疑）都无法回答

**修法（两条，别只做第一条）**：
1. **部署含 ECS 注入的 proxy**——**已就绪**：本地编译产物 `sha256=7ac3604d…`、`rev=b38e94b`、静态 linux/amd64；落后提交里**只有 `63d2577` 动过 `proxy/`**（纯新增），变更面小、可 5 分钟回滚
2. **同时解决上游聚合**：让 `172.16.7.1` 转发时注入 ECS（若该设备支持），或让终端 DNS 直指代理。**否则第 1 条做完，`client_ip` 仍恒为 `172.16.7.1`**

> 由此得出一条对规划的影响：**"多客户端共访"在本次拓扑下是结构性不可用**，不应作为 A1（误伤识别 v2）的依赖特征——A1 必须用不依赖客户端的信号（命中量分位 / 域名年龄 / 业务特征 / 白名单矛盾），这也是 §3 A1 的设计取向。

### 2.3 🟡 关键发现：误伤「已处置完毕」，但全靠人肉发现、滞后 6.7 万~87 万次

拦截量 TOP（全窗口）——**逐条核验了原因与当前状态**：

| 域名 | 历史拦截 | 命中源 | 最后命中 | **当前状态** |
|---|---|---|---|---|
| `devaccess.lechange.cn` | 871,333 | threatintel(DNSBL) | 09-07 | ✅ 已加白（`*.lechange.cn`） |
| `daisy.ubuntu.com` | 106,519 | hagezi_ult | 10-09 | ✅ 已加白（精确） |
| `ws.hanmawin.com` | 70,756 | threatintel(DNSBL) | 09-07 | ✅ 现已放行 |
| `ntp.ntsc.ac.cn` | 69,668 | threatintel(DNSBL) | 09-07 | ✅ 已加白（`*.ntsc.ac.cn`） |
| `ntp.aliyun.com` | 67,429 | threatintel(DNSBL) | 09-07 | ✅ 已加白（精确） |

**准确结论（不要误读成"当前在流血"）**：
- 这批误伤**集中在 09-07 前后、主因是 spamhaus_dbl**（就是 09-10 全网故障的同一元凶，09-10 已停用），此后**每一条都被人逐个加白**，现在全部 `allow`。
- 真正的问题是**发现方式**：这 5 个域在**被拦了 6.7 万~87 万次之后**才由人注意到。也就是"事后人肉发现"，而不是"第一次大量拦截时就报警"。
- **当前仍在的风险**是另一件事：**28 条白名单通配过宽**（`*.lechange.cn`/`*.ntsc.ac.cn`/`*.oss-cn-shenzhen.aliyuncs.com`/`*.qq.com`…）——共享托管型域族整族放行是真实攻击面（银狐就大量用共享 COS/OSS 桶托管恶意内容，当时刻意用精确匹配而非通配）。

**因此 A1（误伤识别 v2）的目标不是"救火"，而是把发现提前**：命中量分位 + 域名年龄 + 业务特征 + 白名单矛盾信号，第一次出现高频拦截就报，不必等 87 万次；同时 A4 把"该放行的放行、该收窄的收窄"分清。

### 2.4 🔴🔴 部署前置阻塞：代理机根文件系统已只读 27 天（磁盘/存储层故障，非本软件问题）

排查 ECS 部署路径时撞到的**更严重的问题**——代理机 `172.16.0.192` 的根文件系统自
**2026-09-17 17:01 起被内核自动转只读**，至今未恢复：

```
[Thu Sep 17 16:57:49 2026] blk_update_request: I/O error, dev sda, sector 35518352 op 0x1:(WRITE)
[Thu Sep 17 17:00:49 2026] sd 0:0:0:0: [sda] tag#657 timing out command, waited 180s
[Thu Sep 17 17:01:26 2026] EXT4-fs (dm-0): I/O error while writing superblock
[Thu Sep 17 17:01:26 2026] EXT4-fs (dm-0): Remounting filesystem read-only
```

| 项 | 状态 |
|---|---|
| 根挂载 | `/dev/mapper/almalinux-root` **`ro,relatime`**（`/`、`/opt`、`/root`、`/tmp`、`/var/log` 全部不可写；仅 `/run`、`/dev/shm` 等 tmpfs 可写） |
| 故障时间 | **2026-09-17 16:57~17:04**（约 7 分钟窗口内 5 次写 I/O 错误，每次超时 180s），此后因只读再无写失败 |
| 影响扇区 | 1232896 / 18286384 / 35049472 / 35518352（分散，**非单点坏道**，更像存储路径/数据存储层中断） |
| **日志** | `/var/log/journal` 不存在 → journald 退化为**内存日志**（`/run/log/journal`，tmpfs），**09-17 至今的 DNS 服务日志重启即丢** |
| 失败单元 | `dnf-makecache` / `sysstat-collect` / `sssd-kcm` / `rc-local`（都是"需要写盘"类） |
| **业务影响** | **DNS 解析仍正常**（在跑进程 + 只读可执行），实测 `dig` 正常应答；平台机 191 一切正常（`rw`、无 ext4 错误、DB 正常写入） |

**对本次规划的两个直接影响**：

1. **ECS 版代理部署被阻塞**：`/opt` 与 `/app` 都不可写 → 既不能 `git pull` 源码，也不能安装新二进制。
   ECS 修复件（`sha256=7ac3604d…`）已就绪，但要**先修好文件系统**才能装上。
2. **不要贸然重启这台机器**：文件系统在报错的存储设备上，重启要走 fsck，若存储未恢复可能**起不来 → 全站 DNS 中断**。当前"在跑进程读只读盘"反而是唯一稳态。

**建议动作（按顺序）**：

| # | 动作 | 说明 |
|---|---|---|
| 1 | **报障给虚拟化/存储团队** | VM `DNS-sec02-172.16.0.192`（UUID `ab263642-06a4-e1f3-6061-8b5dea6ac8d8`，MAC `00:50:56:b6:37:cb`，VMware7,1，磁盘 40G/仅用 4G）→ 查该数据存储的**容量/性能/快照合并状态**（写超时 180s 是典型存储层 stall，容量不是原因） |
| 2 | **维护窗口内先做无重启验证** | `mount -o remount,rw /` 试探存储是否恢复（不必重启）；恢复则立即部署 ECS 版代理并复验 `client_ip`；若写又失败，内核会再次转只读，风险可控 |
| 3 | **准备旁路预案** | 该机是全网唯一 DNS 上游转发目标（`172.16.7.1` → 192），一旦宕机 /etc/resolv 级联失败 → 建议准备好"代理迁到另一台可用 VM"的步骤与备用二进制 |
| 4 | **修好后补日志持久化** | 恢复写盘后确认 `/var/log/journal` 可用，否则下次事故仍无历史可查 |

### 2.5 其他盲区（本次确认）

| 盲区 | 证据 / 说明 |
|---|---|
| **加密 DNS 绕过** | DNS 过滤的天然盲区：终端若启用 DoH/DoT（浏览器自带、Win11 加密 DNS），查询完全不经过我们。日志里有 2,624 行涉及 DoH 提供方域名（多为被拦的追踪域，**不能证明终端在用 DoH**）→ 需要新观测手段 |
| **C2 心跳（beaconing）** | 现有隧道检测是"量/熵"维度；C2 的典型特征是**时间周期性**（固定间隔+抖动），当前无任何时序分析。且 `domain_first_seen` 只记首现、普通放行不记明细 → **缺"客户端×域名 查询计数"数据**，需先补采集 |
| **系统自身异常** | 我们踩过：QPS 骤降（转发路径断）、172.16.0.8 转发器 0 包、上游超时（宵禁）、积压告警 230 次/天阈值噪音（静态常量恰等于稳态值）→ 缺"自身指标基线 + 自适应阈值" |
| **名单条目性价比** | 6,946 条人工黑名单只有 92 个域名真命中过；6 条黑名单通配（含 `*.be` 整比利时 TLD）从未做过影响面评估 |
| **白名单通配风险** | 28 条白名单通配全是大厂域族（`*.qq.com`/`*.taobao.com`/`*.oss-cn-*.aliyuncs.com`…）。**共享托管型域族整族放行是真实攻击面**（银狐就大量用共享 COS/OSS 桶托管，当时刻意用精确匹配而非通配） |
| **情报源闭环** | 质量评分有了（6 源），但"评分 → 建议停用 → 人工执行 → 效果回流"没人做 |

## 4. 路线建议

| 阶段 | 内容 | 理由 |
|---|---|---|
| **P0（本周，1~2 天）** | **A1 误伤识别 v2**（不依赖客户端，可立即开工）+ **B1①** 部署 ECS 版 proxy（待批） | A1 把误伤发现从"人肉滞后 6.7 万次"改为"首次高频拦截即报"，且**不依赖客户端维度**；B1 分两步，②需网络组确认 `172.16.7.1` 是什么设备 |
| **P4（2 周）** | A5 规则影响面预演 + A3 名单质量自省 + A4 白名单通配审计 | 都是"防事故"能力：加规则前先知道会伤谁，把名单从 6,946 条糊成一团变成有账可查 |
| **P5（1 个月）** | D1 自适应阈值 + C2 变更自动复验 + C1 告警推送 + B2 心跳检测（含计数采集） | 从"能发现"到"能叫醒人、能自己恢复、能抓时序威胁" |
| **P6（2 个月）** | B3 加密 DNS 绕过 + B4 基础设施图谱 + D2 LLM 运维助手 | 需要新数据源或外部联动，价值高但依赖多 |

**排序原则**：先补**数据地基**（B1）→ 再提**决策精度**（A 组，纯算法、零依赖、当天见效）→ 再做**防事故的行动安全网**（A5/C2）→ 最后才是需要新数据源的高级感知（B3/B4）。

## 8. 附：本轮顺带加固的部署防线（2026-10-14）

> 起因：代理二进制落后源码 8 个提交、缺失客户端 IP 注入，却从 09-04 平稳运行到 10-14 无人察觉（无报错、无告警，只有"日志里 client_ip 是空的"）。
> **凡是"静默失效"类问题，都要用机制堵，而不是靠人记得。** 本次共加四道：

| # | 防线 | 位置 | 挡住什么 |
|---|---|---|---|
| 1 | **代理二进制自带版本戳** | `proxy/main.go`（`-ldflags -X main.buildRev/buildTime`）+ `-version` 子命令 | 二进制可自证"我编自哪个提交"，不再需要靠猜 |
| 2 | **启动日志显式声明关键能力** | `proxy/main.go` 启动打印 `构建版本：… rev=…` 与 `客户端 IP 注入（EDNS0 ECS）：已启用/已关闭` | 这类事故只需 `journalctl -u proxy \| head` 一行即可判定 |
| 3 | **部署脚本拒绝旧产物** | `deploy/install-proxy.sh` 第 3 步（4 道校验） | ①非 Linux ELF（误用 `make proxy` 的宿主平台产物）②产物比 `proxy/*.go` 旧（mtime）③版本戳 ≠ 仓库 HEAD ④拿不到版本戳时**显式告警**而非静默放过；确需旧产物须 `--allow-stale` |
| 4 | **有 Go 就从源码现编** | 同上 3.1 | 不指定 `--binary` 时优先现编，从根上消除"预编译产物与源码脱钩" |

四道校验已用真实代码段做场景验证（旧产物 / Windows 产物 / 版本戳不符 / 正确产物 / 无版本戳），行为全部符合预期；`make proxy` 目标同步带上版本戳。

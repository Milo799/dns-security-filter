## 1. 判断：AI 能力有四个维度，MCP 只补了其中一维

已有交付（迭代 49 AI 旁路分析 + 迭代 50 MCP）覆盖了前两维，但第三、四维基本空白：

| 维度 | 含义 | 现状 |
|---|---|---|
| **感知**（发现未知） | 从流量里发现规则抓不到的东西 | 部分覆盖：DGA / 隧道 / 族群 / 客户端基线。**但有盲区（见 §2.4）** |
| **决策**（研判与建议） | 把发现变成可判断的结论 | 覆盖：误报评分 / 情报质量 / LLM 中枢。**但精度与自省不足** |
| **行动**（闭环执行） | 让结论真正落地 | ✅ **MCP 已解决**（16 工具，Agent 可操作） |
| **自省**（自身健康与策略质量） | 系统对自己做体检 | ❌ **几乎空白**：名单质量、告警阈值、自身故障自识别都没有 |

一句话：**MCP 解决了「谁在操作」，但「看得更全、判得更准、系统自己会体检」这三件事还没做。**

## 2. 现状盘点：本次生产实测拿到的硬数据

> 全部为只读查询（`platform.db`，2026-10-13 19:5x）。SQL 见 §6，可复现。

### 2.1 数据资产与规模

| 项 | 实测值 |
|---|---|
| `filter_log` 行数 / 时间跨度 | **898.6 万行 / 41 天**（09-02 ~ 10-13），保留期 90 天 |
| 其中 拦截 / 白名单放行 / IP 剔除 | 758.6 万 / 140.0 万 / 7 |
| 唯一被拦域名 | **31,271 个**（其中 **14,536 个只被拦过 1 次** = 46% 长尾） |
| 层分布（行数 / 域名数） | threat_list 612.7 万 / 25,484；threatintel 143.9 万 / 5,770；local_blacklist 2.0 万 / **仅 92 个域名** |
| 人工名单 | 黑 6,946 条（通配 6 条）｜白 65 条（通配 28 条）｜黑白冲突 0 条 |
| 人工黑名单与离线大名单重叠 | 313 条（4.5%） |
| 域名首现表 | 28,873 条（上线 5 小时即 2.7 万，日均约 2.2 万） |
| AI 结论 | DGA 待确认 140、族群 50、隧道 16、情报质量 6；**误报 0 / 失陷主机 0** |

### 2.2 🔴 关键发现：客户端维度 100% 缺失（P0）

| 检查 | 结果 |
|---|---|
| `filter_log.client_ip` | **898 万行全部为空串** |
| `domain_first_seen.first_client` | **28,882 行全部为空串** |
| 平台 ECS 解析 | ✅ **正常**：手工发带 ECS 的查询（`dig +subnet=203.0.113.77/32`），日志正确记录 `client_ip=203.0.113.77` |
| 经代理的查询 | ❌ ECS 缺失：抓包显示转发报文 OPT 记录 **RDLENGTH=0（无任何 option）** |
| 代理二进制 | ❌ 生产 `bin/dns-proxy`（09-04 构建）**不含** ECS 注入代码（`ecs: injected/skip/passthrough` 字符串全为 0；本地重新编译的版本三条全有） |

**后果（不是理论，是已经发生）**：
- 误报识别的最强特征「多客户端共访」（权重 0.32）**永远算不出来** → 生产 `false_positive` 结论 **0 条**
- 失陷主机识别（`client_anomaly`）**永远不产出** → MCP 的 `client_anomalies` 工具、AI 大屏对应面板都是空的
- 任何"按客户端"的研判（谁在被攻击、哪台机器可疑）都无法回答

**修法（已验证）**：重新编译 proxy（本地构建产物含 ECS 能力）→ 灰度部署到 192 → 复验日志出现 client_ip。属于 Go 变更，需动生产 DNS 路径，**须审批 + 备份旧二进制 + 5 分钟内可回滚**。

### 2.3 🟡 关键发现：误伤「已处置完毕」，但全靠人肉发现、滞后 6.7 万~87 万次

拦截量 TOP（全窗口）——**逐条核验了原因与当前状态**：

| 域名 | 历史拦截 | 命中源 | 最后命中 | **当前状态** |
|---|---|---|---|---|
| `devaccess.lechange.cn` | 871,333 | threatintel(DNSBL) | 09-07 | ✅ 已加白（`*.lechange.cn`） |
| `daisy.ubuntu.com` | 106,519 | hagezi_ult | 10-09 | ✅ 已加白（精确） |
| `ws.hanmawin.com` | 70,756 | threatintel(DNSBL) | 09-07 | ✅ 现已放行 |
| `ntp.ntsc.ac.cn` | 69,668 | threatintel(DNSBL) | 09-07 | ✅ 已加白（`*.ntsc.ac.cn`） |
| `ntp.aliyun.com` | 67,429 | threatintel(DNSBL) | 09-07 | ✅ 已加白（精确） |

**准确结论（不要误读成"当前在流血"）**：
- 这批误伤**集中在 09-07 前后、主因是 spamhaus_dbl**（就是 09-10 全网故障的同一元凶，09-10 已停用），此后**每一条都被人逐个加白**，现在全部 `allow`。
- 真正的问题是**发现方式**：这 5 个域在**被拦了 6.7 万~87 万次之后**才由人注意到。也就是"事后人肉发现"，而不是"第一次大量拦截时就报警"。
- **当前仍在的风险**是另一件事：**28 条白名单通配过宽**（`*.lechange.cn`/`*.ntsc.ac.cn`/`*.oss-cn-shenzhen.aliyuncs.com`/`*.qq.com`…）——共享托管型域族整族放行是真实攻击面（银狐就大量用共享 COS/OSS 桶托管恶意内容，当时刻意用精确匹配而非通配）。

**因此 A1（误伤识别 v2）的目标不是"救火"，而是把发现提前**：命中量分位 + 域名年龄 + 业务特征 + 白名单矛盾信号，第一次出现高频拦截就报，不必等 87 万次；同时 A4 把"该放行的放行、该收窄的收窄"分清。

### 2.4 其他盲区（本次确认）

| 盲区 | 证据 / 说明 |
|---|---|
| **加密 DNS 绕过** | DNS 过滤的天然盲区：终端若启用 DoH/DoT（浏览器自带、Win11 加密 DNS），查询完全不经过我们。日志里有 2,624 行涉及 DoH 提供方域名（多为被拦的追踪域，**不能证明终端在用 DoH**）→ 需要新观测手段 |
| **C2 心跳（beaconing）** | 现有隧道检测是"量/熵"维度；C2 的典型特征是**时间周期性**（固定间隔+抖动），当前无任何时序分析。且 `domain_first_seen` 只记首现、普通放行不记明细 → **缺"客户端×域名 查询计数"数据**，需先补采集 |
| **系统自身异常** | 我们踩过：QPS 骤降（转发路径断）、172.16.0.8 转发器 0 包、上游超时（宵禁）、积压告警 230 次/天阈值噪音（静态常量恰等于稳态值）→ 缺"自身指标基线 + 自适应阈值" |
| **名单条目性价比** | 6,946 条人工黑名单只有 92 个域名真命中过；6 条黑名单通配（含 `*.be` 整比利时 TLD）从未做过影响面评估 |
| **白名单通配风险** | 28 条白名单通配全是大厂域族（`*.qq.com`/`*.taobao.com`/`*.oss-cn-*.aliyuncs.com`…）。**共享托管型域族整族放行是真实攻击面**（银狐就大量用共享 COS/OSS 桶托管，当时刻意用精确匹配而非通配） |
| **情报源闭环** | 质量评分有了（6 源），但"评分 → 建议停用 → 人工执行 → 效果回流"没人做 |

## 3. 候选能力清单（13 项）

### A. 决策精度（把现有 AI 做准）

| # | 能力 | 缺口与做法 | 数据 | 工作量 |
|---|---|---|---|---|
| A1 | **误伤识别 v2（不依赖客户端）** | 新增"高频拦截 + 业务域名特征"评分：命中量分位、域名年龄、TLD 属性、主域是否含业务词、是否已被人工加白（矛盾信号）。**立刻可跑**，不用等客户端数据 | filter_log + nrd_cache + 首现表 | 2~3 天 |
| A2 | **DGA 精度提升 + 反馈自校准** | ① 词形分割（`zlwh2026`→`zlwh`+`2026`，识别拼音缩写/业务词根）② 用人工 `confirmed/dismissed` 反哺权重（现在这两个状态没人用） | ai_findings 状态 + 首现表 | 3~4 天 |
| A3 | **名单质量自省** | 产出三张清单：**僵尸条目**（长期零命中，可归档）、**过宽条目**（通配/整 TLD，给影响面）、**矛盾条目**（命中后又被人工加白） | filter_list + filter_log | 2~3 天 |
| A4 | **白名单通配风险审计** | 识别共享托管型域族（OSS/COS/FaaS/短链/CDN）整族放行风险，建议收窄为精确子域 + 保留例外清单 | filter_list + 银狐案例 | 1~2 天 |
| A5 | **规则影响面预演（影子模式）** | **加规则前先算影响面**：候选规则（加黑/加白/通配）对最近 N 天真实查询回放，产出"会影响 X 台客户端 / Y 个域名 / Z 次/天 + 抽样清单"，人工看报告再决定启用。MCP 可在 `blacklist_add` 前自动跑 | filter_log（898 万行样本） | 3~5 天 |

## 4. 路线建议

| 阶段 | 内容 | 理由 |
|---|---|---|
| **P0（本周，1~2 天）** | **B1 客户端维度上线**（重建 proxy）+ **A1 误伤识别 v2** | B1 是所有"按客户端"能力的地基（已定位为部署问题、本地编译已验证）；A1 把误伤发现从"人肉滞后 6.7 万次"改为"首次高频拦截即报" |
| **P4（2 周）** | A5 规则影响面预演 + A3 名单质量自省 + A4 白名单通配审计 | 都是"防事故"能力：加规则前先知道会伤谁，把名单从 6,946 条糊成一团变成有账可查 |
| **P5（1 个月）** | D1 自适应阈值 + C2 变更自动复验 + C1 告警推送 + B2 心跳检测（含计数采集） | 从"能发现"到"能叫醒人、能自己恢复、能抓时序威胁" |
| **P6（2 个月）** | B3 加密 DNS 绕过 + B4 基础设施图谱 + D2 LLM 运维助手 | 需要新数据源或外部联动，价值高但依赖多 |

**排序原则**：先补**数据地基**（B1）→ 再提**决策精度**（A 组，纯算法、零依赖、当天见效）→ 再做**防事故的行动安全网**（A5/C2）→ 最后才是需要新数据源的高级感知（B3/B4）。

## 5. 需要你拍板的决策点

| # | 决策 | 我的建议 |
|---|---|---|
| 1 | **是否本周重建并部署 proxy（B1）** | **建议做**。这是"客户端维度"的唯一堵点，已本地编译验证；但它是生产 DNS 路径的 Go 变更——我会先备份旧二进制、错峰部署、5 分钟内可回滚，需要你同意动手窗口 |
| 2 | P0 之后优先做 A 组（决策精度）还是直接上 D1（自适应阈值） | 建议 **A 组**：A1 立刻能产出误伤清单（真实痛点），D1 是降噪（不痛但烦） |
| 3 | 误伤识别 v2 的默认动作 | 建议 **只出清单 + 证据，不自动加白**（沿用红线）；对"命中量 TOP + 已人工加白历史"的域名可给强建议 |
| 4 | 白名单通配（28 条）是否收紧 | 建议**审计后逐条人工定**：共享托管型（OSS/COS/短链）建议收窄；大厂自有域族（`*.qq.com`）可保留 |
| 5 | C1 告警推送通道 | 需你定通道（企业微信/邮件/短信），涉及审批；不定就走"日报样式"先落 MCP + 每日摘要 |
| 6 | B2 心跳检测要新增采集（客户端×域名计数） | 建议**跟随 B1 一起做**（都在动 proxy/平台数据面），避免二次改动 |

## 6. 附：本次盘点的可复现命令

```bash
# 客户端维度缺失（两侧都空）
sqlite3 -readonly platform.db "SELECT COUNT(DISTINCT client_ip) FROM filter_log WHERE client_ip<>''"
sqlite3 -readonly platform.db "SELECT COUNT(DISTINCT first_client) FROM domain_first_seen WHERE first_client<>''"

# 平台 ECS 解析是否正常（应记到你指定的 subnet）
dig @127.0.0.1 -p 15353 +subnet=203.0.113.77/32 xybpoxl.biz A
sqlite3 -readonly platform.db "SELECT client_ip,domain FROM filter_log ORDER BY id DESC LIMIT 1"

# 代理二进制是否含 ECS 注入（0 = 需要重建）
strings /opt/dns-security-filter/bin/dns-proxy | grep -c 'ecs: injected'

# 误伤线索：拦截量 TOP
sqlite3 -readonly platform.db "SELECT domain,COUNT(*) c FROM filter_log WHERE action='intercept' GROUP BY domain ORDER BY c DESC LIMIT 20"

# 名单条目性价比
sqlite3 -readonly platform.db "SELECT COUNT(DISTINCT domain) FROM filter_log WHERE filter_reason LIKE 'local_blacklist%'"
```

## 7. 一句话总结

> **MCP 让 Agent 能操作这个系统；这份方案让这个系统「看得更全（客户端/加密 DNS/心跳）、判得更准（误伤/DGA/名单质量）、自己会体检（自适应阈值/根因）」，并且给规则变更装上「影响面预演 + 自动复验」的安全网——第一条（客户端维度）现在就堵着，且已经查清是部署问题。**
